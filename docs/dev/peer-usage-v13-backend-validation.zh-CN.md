# v1.3 设备用途后端实现与验证记录

日期：2026-10-26。对应 [前端接口文档](peer-usage-frontend-integration.zh-CN.md) 与 [产品需求](../product/extended-display-requirements.zh-CN.md)。

本记录区分代码实现、隔离运行验证与双机验收。当前已经接入产品服务、真实认证连接观察、输入协议和原生媒体运行适配器；尚未完成 Mac ↔ Ubuntu 两台设备上的完整输入/副屏切换验收，不能据此发布为三平台全面支持。

## 本次实现

- `queryConnectedPeerUsage` 查询既存认证连接，提供基础连接 UUID/代次、原 source/receiver 角色与方向、实际路由、权限、焦点和用途；变更命令必须绑定准确连接。
- 认证 TLS/蓝牙隧道通过实际回环套接字映射原生连接，GUI 名称、IP、设备索引不能成为认证凭据。断线关闭旧连接，待清理期间保留旧资源归属，新连接不能接收旧回调。
- 原输入两种角色均支持撤权、释放确认、准备与恢复提交。权限准备不等于输入已生效；源端通过协议发布实际路由状态。
- 显示授权、允许/拒绝、准备和停止沿既存认证流传送；独立 LAN 媒体通道使用证书绑定与双向 TLS。私钥保留本地，不通过控制流传送。
- `ProductDisplayRuntime` 装配真实平台探测、`MediaSupervisor`、原生捕获与接收窗口。接收端先完成输入释放，发送端先获得系统捕获权限；双方都满足后才创建副屏。首帧必须来自原生窗口呈现及认证对端确认。
- `retryPeerUsageCleanup` 统一清理输入与显示残留；主窗口支持启动恢复清理。资源日志不恢复显示授权，不按日志中的 PID 或名称删除其他资源。
- 显示转回键鼠必须等待本端与对端清理证据。旧基础连接已关闭时只处理本地资源，不凭旧授权自动建立输入。正常结束扩展不会自动控制对方桌面。
- 输入暂停和显示资源占用持久化为本地互锁，防止核心重启或输入传输重连绕过暂停；选择偏好不能启动用途。
- `presentReceiverWindow`、`setReceiverPresentation` 提供真实显示、最小化/恢复、屏幕选择、全屏/窗口状态确认。
- `queryDisplayLayout`、`setDisplayLayout` 返回和修改当前实际虚拟屏的系统逻辑布局。命令在持有虚拟屏的原生进程中执行；旧会话不能凭可复用的显示器名字修改新资源。GNOME 与 CoreGraphics 均有实现，macOS 尚缺运行验收。
- `streamConfig` 来自媒体协商；没有可靠测量的统计保持 null。目标 30fps 不等于实测达到 30fps。

## Ubuntu 实际媒体与布局验证

手动运行目标 `ProductRuntimeSmoke`，通过 `tools/virtual-display-prototype/validate_product_runtime.py` 创建临时身份与隔离资源目录。验证使用 Ubuntu 现有 GNOME 会话的显示、会话总线及 Xauthority 环境，不替换用户正在运行的 GUI/核心。

此程序在**同一 Ubuntu 图形会话内运行两个产品服务端点**：媒体连接为真实双向 TLS，GNOME 虚拟输出、捕获、H.264 编解码和 Qt 原生接收窗口真实运行；认证控制消息在隔离测试中转发，输入 ACK 使用模拟适配器。它不代表两台设备的真实键鼠硬件验证。

两次相反方向均通过：

1. 探测能力后发起，接收方仅本次允许；真实首帧才生效为 extended。
2. 查询系统显示拓扑，将当前虚拟屏移动到主屏下方，核对系统确认坐标，再恢复原位置。
3. 显示画面、适应窗口/原始大小、全屏、退出全屏并最小化、恢复；不存在的屏幕被拒绝。
4. 第一次切回键鼠时，故意扣留对端清理消息；本端资源已释放仍不恢复输入，补送清理证据后才继续。
5. 停止后两端均回到 Idle，资源清理 verified，正常结束不自动开启输入。

结构化结果：

```json
{"passed":true,"directions":2,"nativePresentation":true,"inputHardwareVerified":false}
```

临时证书不会提交仓库。验证失败时脚本仅在系统临时目录保留资源归属证据，不把失败当清理成功。

## 仅蓝牙策略后端适配（2026-10-26）

连接管理器向原生连接观察发布明确的 `displayNetworkPolicy`。共享端仅蓝牙、接收键鼠端蓝牙初始连接且关闭网络备用时为 bluetoothOnly；允许网络备用但当前活动通道为蓝牙时仍为 networkAllowed。托管连接策略尚未发布时保持 unknown，不提前开放显示网络能力。

双方通过既存认证控制流交换策略；`displayNetworkAllowed` 与 LAN 地址可用性独立。任一端禁止时，开始、切换、接收请求及下层显示服务均拒绝，返回 BluetoothOnlyMode，不申请授权、不释放既存输入、不创建视频连接。界面禁用扩展按钮并说明需要先启用网络。

策略撤销时，等待授权阶段取消且保留输入；已经开始资源准备或扩展时执行清理并禁止自动恢复输入。重复策略通知不重置正在执行的清理代次。仅能力/策略发生变化也递增快照修订号，避免前端忽略新的禁用或重新启用状态。

验证包括：LAN 已可用仍拒绝蓝牙模式、直接 API 和下层 API 无法绕过、源端/接收端连接策略发布、未知托管策略禁止提前开放、迟到允许不能复活、重复撤销清理幂等、前端禁用与提示、重新允许网络后重新探测。完整回归 131 项通过。

Ubuntu 双端隔离媒体联调另验证了策略传播、恢复许可后仍可运行真实媒体、扩展期间撤销许可后双端回到 Idle 且清理 verified。输入 ACK 仍使用模拟适配器；没有新增物理蓝牙或 Mac ↔ Linux 双机验收结论。LAN 实际连通性/TLS 的前置探测仍是独立待完善项。

## macOS 空显示 ID 的历史清理恢复（2026-10-27）

- 原故障：中断的 host 会话已写入资源归属，但 displayId 尚为空。旧恢复检查直接返回失败，导致“待清理”永久阻止后续用途。
- 原生 probe 通过 CGGetOnlineDisplayList 枚举在线输出（包括非活动输出），报告本后端 vendor/product 对应的 deskflowVirtualDisplays。仅当 macOS host 的空 ID 记录遇到明确空列表时，才确认资源已不存在并清理日志。枚举失败、字段缺失、发现残留、进程异常退出或非零退出都保留待清理；空 ID 的 receiver/Linux 记录不使用此恢复推断。
- 恢复仅检查不存在，不按名称或历史 PID 删除显示器或结束其他进程，不重新申请显示授权，也不自动启用键鼠或视频。
- UnknownHostResourceRecovery 覆盖空列表、残留列表、缺失字段、null、无效 JSON、receiver/Linux 限制、非零退出和信号终止。RecoveryAdoptsPendingConnection 覆盖统一清理后采用待接入基础连接且不自动启用用途。
- Ubuntu 与 Mac 均编译成功，Display.Service / Display.UsageService 各 38 项 CTest 全部通过。
- Mac 实机：原生只读探测得到 deskflowVirtualDisplays=[]，物理显示列表前后均为 [3]。从设备详情点击“重试清理”后警告消失，资源日志变为 active:null。更新原开发证书签名的预览应用并正常重新启动后，原故障设备仍无清理警告；目前基础连接未启动，仅显示“请先建立连接”。本次没有新增首帧或双机拓展成功验收结论。
